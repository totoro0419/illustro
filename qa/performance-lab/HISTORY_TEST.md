# Undo・Redo・保存の整合性 — 独立検証（History Lab）

**日付：2026-10-30 JST**　**実装**：[`history.html`](history.html)（JavaScriptを内蔵した単独HTML）。

[ブラウザ公開予定ページ](https://totoro0419.github.io/illustro/qa/performance-lab/history.html) ／ [統合製品仕様](../../docs/product-planning/FINAL_PRODUCT_SPEC.md)

## 目的と検証対象

ペンの受理、Revision作成、Undo/Redo、正式画素への非同期確定、保存要求時点のスナップショット、保存完了後の再読込について、**整合性が崩れないか**を検証する。本体のPainter/Worker/OPFS/Tileとは独立している。

- 受理した線は、描画の正式計算終了前から独立したRevisionとして履歴に追加。
- Undo/Redoは表示用画素を現在の履歴Rootから再生成。正式な計算が遅れても、古いRevisionの結果を再公開しないようepochで判定。
- 正式計算は、各Revisionに含まれる筆跡を受理順に評価してから、現在Revisionと一致する場合に限り1枚のCanvasへ結果を置換。画素差があれば公開しない。
- 保存ボタンを押した瞬間のRootと画素ハッシュを固定。非同期保存完了までにUndo・追加描画が起きても、保存対象を変更しない。
- 連続する保存要求を**順序通り処理**し、最後に要求したRootがブラウザ側ストレージの最新状態になる。
- 実ブラウザではIndexedDBへのトランザクション完了後に読戻し、正本画素ハッシュとの一致を調べる。テスト環境ではストレージAPIをシミュレートする。
- マウス・ペンによる手描きと、1本指パン・2本指拡縮回転が可能。操作回数、最長イベント受付遅延、正式処理中の最長rAF間隔、正式画素差、破棄した古い計算数を記録。

## 自動化した8シナリオ（ローカルChromium）

| # | ケース | 結果 |
|---|---|---|
| 1 | 計算待ち中Undo後に古い線が復活しない | PASS |
| 2 | Pending Undo→Redoで同一筆跡を復元 | PASS |
| 3 | 2本の線を受理順に正式処理、結果一致 | PASS |
| 4 | Save(A)要求→Undo(A)→保存されたRootはA | PASS |
| 5 | Save(A)→Save(A+B)、Undo(B)しても最終保存RootはA+B | PASS |
| 6 | 保存版読込後の再計算・画素ハッシュ一致 | PASS |
| 7 | Undo後の新筆受付でRedo分岐が消える | PASS |
| 8 | 計算中Reset後に旧計算結果が再表示されない | PASS |

**確認方法**：Playwright+Chromiumの単一HTML直接ロード。検査ブラウザではローカルHTTPの遷移が環境によってブロックされるため、**自動テスト4〜6の保存部分のみIndexedDB APIを模したインメモリ・ストレージで検査**。したがって、実IndexedDBのトランザクションやブラウザ再起動後の耐久性が8件PASSで証明されたわけではない。

## 補助ブラウザスモーク

- 1本の計算中にSave→Undo→保存処理完了→Load：履歴・画素一致。
- 390px幅モバイルレイアウト：横スクロールなし。
- Chromium CDP合成2本指のナビゲーション：正式計算中の指イベント26件、キャンバス拡縮・回転、計算結果差分0。
- JSON出力：ブラウザからファイル保存を確認。JavaScriptページエラー：0件。
- 本体画像は448×320 RGBA 8bitの単一レイヤーに限定。**人工待機2秒は負荷ではない**。

## 製品方式へは未採用

この検証だけで、GPU/Worker、確定前Undoと同時保存の実製品実装、高精度ICC/特殊レイヤー合成、複数Tileの公開原子性、端末停止・電源断からの保存復旧、保証されたpen-to-photon性能を達成したとは言えない。

**Android実機での次の実験**：公開ページで「8シナリオを検査」→「太い線を追加」→正式処理中に「現在の作品を保存」→「Undo」→保存完了後に「保存版を読み込む」→「結果JSONを保存」。JSONと目視異常の有無を確認する。

未実施：Android上でのネイティブIndexedDBの実読込/永続性、GPU高負荷、作品本体の保存・復元・Undoの実装。

## 技術上の注意

この検証ページは、毎Revisionの画素全体を再生成して比較する**小規模な正しさ優先のモデル**であり、そのまま製品の大きなキャンバスに適用して高速化できる方式ではない。保存のハッシュ（FNV32）はテスト用の非暗号学的検査値。破損・衝突まで保証するデータ整合方式ではない。
