# Illustro UI起点・操作連続性検査 実行手順

- 作成：2026-11-20
- 検査対象：`quality/painting-workspace-ux`（PR #101）のUI。比較基準：`quality/C03-C10-integration`。
- 初回のUIコード基準コミット：`1ab6ea2d9d12beea18e9f8165ada0b3d716264b5`。実行時は最新コミットを確認する。
- 対象操作の基準：`quality/C03-C10-integration:docs/quality/M01-M10-CONTINUOUS-OPERATIONS.md`（33シナリオ、T001～T827）。
- UI要素の初期台帳：`quality/painting-workspace-ux:docs/quality/UI-FIRST-CONTROL-INVENTORY.json`。
- 目的：機能の存在確認ではなく、「画面で見つかる → 押せる → 期待した結果が起こる → 自然に次の操作へ移れる → 戻れる」を検査する。
- 段階：調査・検査。明示的な修正依頼までは、アプリ本体の修正をしない。

## 実施順序・担当

### 1. Chat：UIの全入口をコードから確定
1. 初期台帳を読み、`homeShell.ts`、`shell.ts`、`color/panel.ts`と、各UIが動的に生成する要素を調べる。
2. 現在のCSS・`shellBehavior.ts`・`main.ts`を読み、ホーム、作品作成、描画、ブラシ、色、レイヤー、保存/出力、その他のパネル・メニューを画面別に分類する。
3. 各操作を `画面→押す部品→開く画面または実行する処理→その後にできること→戻り方` として整理する。
4. 初期の `disabled` と、実行時に有効になる条件は区別する。UIのコードだけでは実機の表示・クリック可能性を「成功」と判定しない。
5. M01～M10に含まれる操作と、後発のC系機能を区別する。後者も見える入口を台帳に記録するが、M10基準に無理に組み込まない。

**成果物**：UI操作経路の一覧（画面/部品ID/前提/押した結果/ハンドラ/次の操作/戻り方/根拠ファイルと行/対象範囲/確度）。

### 2. Chat：接続の静的検査
1. 各部品のイベント処理、実際に呼ばれる機能、状態の更新先、表示・非表示の条件を追う。
2. 「入口なし」「反応処理の疑い」「メニューへ行けるが戻れない」「切替後の状態が意図せず残る」「表示上使えそうだが準備中」を**要確認候補**にする。
3. T001～T827と照合する。各項目がどの画面経路に対応するか、対応経路がないか、実機でないと判定できないかを記録する。
4. 実機でしか確定できない指/ペン/視認性/体感速度は保留する。未確認を失敗・成功に変換しない。

**成果物**：既知のコード上の根拠、問題候補、ブラウザで確認する優先経路、827項目との対応表。

### 3. Work：UIを実際に見て、コードの地図を検証
1. 現在の作業ブランチからビルドし、必要に応じて公開プレビューとの版の違いを調べる。
2. 既存のPlaywright検査（`scripts/editor-home-smoke.mjs`、`scripts/editor-m08-smoke.mjs`、`scripts/editor-m09-smoke.mjs`、`scripts/m10-brush-editor-review.mjs`、`scripts/editor-works-safety-smoke.mjs`等）を再利用する。
3. 新規の隔離されたテスト作品を使用し、初期画面からユーザーと同じ順序で遷移する。画面ごとに表示中・押せる・使用不可・見えない部品を記録する。ソースにあるだけで画面にないボタンを押したことにはしない。
4. PC/タブレット/スマホ相当の画面を確認。非表示メニュー、スクロールの奥、画面の重なり、押した後の戻り道を検査する。
5. 一括全画面スクリーンショットは不要。失敗箇所と必要な状態遷移に限って証拠を残す。

**成果物**：現実のUIを反映した操作経路、静的調査との相違、未到達入口と再現手順。

### 4. Work：自然な連続操作を実行
1. 33シナリオを出発点に、描く→色変更→描く→レイヤー追加→描く→元に戻す→保存→開き直す、などの連続操作を実行する。
2. 1手ごとに初期化しない。作品・レイヤー・ブラシ・色・履歴・開いている画面の状態を引き継ぐ。
3. 操作後の結果を、画面表示だけでなく検証可能なデータ（描画線、選択レイヤー、保存データ、履歴の変化など）で照合する。
4. 失敗時は該当操作ID・直前の操作・状態・期待値と実際の結果・スクリーンショット・該当コード・再現性を記録する。
5. 既存作品を削除しない。削除・初期化はテスト専用データに限定。破壊的操作を本番状態へ適用しない。
6. 失敗で全827件を最初から再走しない。該当経路と依存範囲を再検査する。自動化に不向きな項目は根拠付きの未確認にする。

**成果物**：項目ごとの `成功/失敗/画面にない/対象外/未確認`、連続シナリオ結果、再現可能な問題報告。

### 5. Chat：検査結果を判定し、次の修正範囲を確定
1. Workのログやスクリーンショットとコードの根拠を突き合わせる。
2. 同じ原因の失敗はまとめ、実害と再現性から優先順位を付ける。
3. 真の機能不足と、見つけにくいだけのUI問題を区別する。
4. 修正の必要なファイル・操作・完成条件を具体化する。変更と再検査が必要な段階でWorkに渡す。

## 判断基準

- **コード上で接続を確認**：UI入口と呼出先が静的に追える。画面で押せたことまでは意味しない。
- **ブラウザで確認**：実際の画面から操作が届き、結果が測定された。
- **Android実機で確認**：指/ペン入力、操作感、端末の表示・遅さなどを本人の端末で確認した。
- **問題候補**：原因や再現が未確定。成功・失敗と混ぜない。

## 調査を効率化する約束

- 初期台帳は機械抽出した出発点にすぎず、336行のすべてが独立したボタンや実行可能な操作とは限らない。入力欄、開閉見出し、重複生成箇所、動的部品を区別する。
- まずユーザーの「見える操作」を追い、内部機能一覧から無差別に機能を調べない。
- 既存のテストを再利用し、合格済みの内容を根拠なく重複検査しない。ただしUI変更で影響した範囲は再確認する。
- M10以降の機能は検出・分類するが、M10だけの検査件数には混入しない。
- 報告は結果中心。完了宣言には、実行対象コミット、試験件数、失敗・未確認件数を必ず付ける。
