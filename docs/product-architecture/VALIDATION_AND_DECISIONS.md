# 検証計画・未決定事項

## 1. 技術案の根拠・代替・欠点

| 項目 | 第一候補と根拠 | 代替案・欠点 | 採用前に測ること |
|---|---|---|---|
| 入力と表示 | 小さい入力処理とView更新、重い正式評価を分離。R01/02 | Main同居分割は簡単だがCPU競合。Worker分離はIPC/転送。GPUは帯域と投入済仕事の制約 | 実機の配送→受付→表示、p50/p95/p99、最古筆の前進、総確定時間、温度 |
| 仮線→本線 | 一筆の整合した世代を一括公開。PR #6は小規模成立例 | タイル部分公開は早いが排他的被覆・halo・透明度・Undoが複雑。一括は確定遅延・一時資源 | 半透明、消去、Mask、Clip、深いGroup、異なる仮/正式方式で欠落・二重・色差 |
| Brush評価 | 特性契約に基づくR03 A/B/C/D/Eの少数経路 | 全筆を中心線方式へ統一するとflow/質感/混色の順序を失う可能性。専用経路は保守費 | 参照画像と筆圧/入り抜き/合成の同等性、転送含む速度、仮線生成費 |
| Tile/dirty | タイルと内部部分域を状況で切替。R05 | 細分化は探索・Mask・投入固定費。全タイルは計算の無駄が増える | 同品質で部分/全体/全域、halo、境界規則、全体統計/変位の遠方依存 |
| Layer合成 | 同値区間の上下キャッシュ＋hot set。R06 | 全層毎フレームは重い。RGBA上下2枚固定は特殊合成で不正確 | blend/clip/Group/階調依存/色精度、選択切替、ピークメモリ |
| 履歴 | 不変ブロック共有＋差分、hot/cold。R07/08 | 全snapshotは容量大、全筆再演は復元時間が増える。圧縮はCPU費 | 未確定Undo/Redo連打、保存pin、分岐、メモリ圧、同じ画像の復元 |
| 保存 | 変更ブロック＋manifest世代＋確認後公開。R07/13 | API別の耐久保証差。一時容量は必要。全ファイルcopyは簡単だが大作品に不利 | Android/Windowsで書込途中終了、quota、権限、外部変更、旧正常世代維持 |
| 色 | 明示したsRGB/P3・8U/16U/16F契約。PR #5 | 高精度はメモリ/演算費。8Uへ無言縮退は不可。ICCライブラリ互換差 | α0/半透明、U16/F16、assign/convert、Proof、codec往復、厳密式と許容差 |
| 非破壊変形 | 原本＋設定＋後段描画＋再生成cache。PR #5 | 単純逆写像は折返しで不成立。毎回焼込は再編集性を壊す。ノード増加は評価費 | 変形→描画→旧変形再編集、後段の位置幅、整数Pixel、保存・Undo |
| 遅延起動 | 宣言と本体ロードを分離。R14 | 初回起動待ち。根拠なき先読みは通常描画へ干渉 | 初回/再利用/閉じた後、アイドルCPU/GPU、メモリ漏れ、需要時進行 |
| 観測 | counterのStatusSnapshot、画素検証は明示Job。PR #6の教訓 | 状態キャッシュ自体が古くなる危険。低頻度更新だけでは本質解決にならない | 状態照会でrender/hash/readbackが増えないこと、診断ON/OFFの比較、値の正しさ |

すべて実装候補。独立CPU Labの成功で製品GPU/Workerの成立を証明しない。単なる人工待機を高負荷と呼ばない。

## 2. 技術検証の実験単位

| ID | 実験 | 合否の意味 |
|---|---|---|
| T01 | 8U単層の正式筆＋仮線＋ナビ、異なる経路と参照方式を比較 | 画素差許容契約、欠落/二重0、順序/位置一致。性能閾値は計測前に別途明記 |
| T02 | 同じものを複数層、Mask、Clip、Multiply/Groupへ拡張 | 正しい層位置、正式合成と比較。単層の合格を流用しない |
| T03 | pending筆→Save→Undo→新筆→古い完了→再読込 | 対象版・branch・保存順一致。失敗0を要求 |
| T04 | 分割GPU仕事とViewの競合、Main/Worker候補比較 | 指ナビと最古筆がともに前進。GPUの自由な割込みを前提にしない |
| T05 | 全域Fill/大半径blur/変位/位相更新 | 入力域の正確性、境界差0、候補と正式の分離、独立操作維持 |
| T06 | Device loss、容量不足、Job失敗、素材欠落 | 正本と旧正常世代保護、局所失敗、復旧導線。成功偽装0 |
| T07 | 16U/F16/ICC、変形後筆、Nativeと外部形式 | 値・外観・編集性・損失を別評価。無言降格0 |
| T08 | 100/1000層、長時間、複数文書、深い効果 | 目標条件の明記、メモリ/温度/電池、cold復帰。極端条件と通常条件を区別 |

各実験ではハードウェア・OS・ブラウザ・DPR・表示Hz・作品条件・入力系列・背景状態・反復回数を固定して記録。OS配送、JS受付、描画要求、GPU完了、表示発光を可能な計測手段ごとに分ける。rAF間隔をそのまま発光遅延や一定FPS保証とみなさない。

## 3. UIの実機評価課題

名称を教えず「髪の色を塗るが線は別の層」「描いた内容だけ向きを直したい」「紙面の表示だけ反転して確認」「後から変形を直して線を加えたい」「過去の別案へ戻す」「透明PNGを出す」を提示する。PC、タブレット横/縦、スマホで、到達率・最初の操作・探索時間・誤対象・不要な閉開・視線/手移動・Canvas遮蔽を記録。

主機能の空間安定性、単指・非ドラッグ代替、Focus解除、キーボード順、200%拡大/320px幅、文字入力/IME/ソフトキーボード、safe-area、画面回転を確認する。スクリーンリーダー実機はDOM semanticsの検査と別に行う。

プロトタイプの単体HTMLは通信不要で開けるが、ブラウザのローカルファイル制限やWebView制限は別条件。見えないPopupの透明hit areaを残さない。閉じたWorkspaceはDOM/CSS上も非操作とし、単なる透明化で隠さない。

## 5. 引渡し判定

設計資料と導線試作はレビュー可能にする。製品実装へ渡す契約・テスト課題を具体化したが、UIの最終承認とT01–T08の技術採用は未実施。技術検証に失敗した場合は境界契約を守る代替方式を比較し、製品体験の変更が不可避な場合だけ明示的に仕様差分を提案する。
