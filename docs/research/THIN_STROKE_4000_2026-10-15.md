# Thin strokes on a 4000px canvas

Status: EXPERIMENTAL. Automated/browser results do not establish physical Android performance or user acceptance.

Base: PR28 `efaf43766aa96befa18984f34d8853543c7d7eed`, tree `ce4808ca868938068e9de942d123c592120c8219`. This preserves the additional color-wheel fixes, ordered stroke handoff, continuous Undo and wide-brush work reduction. No prior PR or production branch is merged or overwritten.

## Measurement and feasibility

The first mobile-width comparison covered actual 8/16/32/64px G-pen input at4000². Previous submissions were dominated by repeatedly shading the whole backing image, including unchanged pixels and frames with no changed tile. WebGPU repeated unchanged presentation took about75ms in the local SwiftShader environment. This includes browser/queue completion and is not isolated GPU execution time. Tile-local scene work and mip draw counts also increase with document-space path length.

Adjacent mip rectangles alone reduced command counts but had a small/noisy effect on elapsed time. Merely reducing formal batches to16 made the queue settle more slowly and was rejected. The chosen design combines reuse of final screen pixels, exact rectangle unions, omission of redundant intermediate feedback, and a maximum32 formal batches per submission while input is active. Idle/ended input and atomic held history reconstruction use up to128, still within the existing pixel-work budget. The existing pixel-work budget, ordered canonical jobs and admission/memory bounds remain in force. The first CI candidate kept the32-batch cap even after input stopped; submission counts grew and several narrow-brush total times regressed despite better active display medians. Its1100-stroke mobile stress accepted281 strokes, so publication was blocked. The revision restores larger bounded idle batches, omits unchanged automatic WebGPU copies, and retains refusal diagnostics before stress assertions. A matched three-trial WebGL2 comparison then found that full-viewport blits still copied128.4million pixels per four strokes. Dirty-only blits reduced this to0.72million, increased completed presentation requests from70 to93 per trial and reduced active completion p95 from68.5 to58.3ms; total paced-stroke medians were effectively equal. Exact backing-pixel comparisons remained unchanged. These changes require a new exact-source CI run; the failed candidate is not an accepted result.

A local matched, alternating, three-trial comparison of16px strokes gave active-input submission-completion medians101.4→27.85ms on WebGL2 and202.9→115.7ms on WebGPU. Four-stroke total medians2813.8→2658.7ms and2972.0→2674.7ms include the same paced input. First-stroke input latency did not improve uniformly in every trial. These are preliminary software-GPU measurements; the exact-source CI evidence supersedes them. No all-device one-frame/4000px smoothness claim is made.

## Implemented plan

1. Keep one RGBA8 image at the actual screen backing dimensions, capped at32MiB. It is derived display state, never artwork, history, save data or the only representation of a stroke. There is no additional4000² history/preview copy. Old viewport images are released on resize and destruction.
2. Reuse the unchanged presentation shader, image sampling, rotation, paper and shadow. Project changed document tiles conservatively to screen rectangles, including mip/area/bilinear sampling support and a rounding guard. Recompute only their exact union. WebGL2 blits only the changed rectangles from the completed screen image into its preserved drawing buffer; WebGPU copies it with a one-texel-load render pass. RGBA8-to-RGBA8 preservation is independently checked against direct rendering.
3. Track screen invalidation independently of mip invalidation, including100% views where no mip is used. Initial render, changed view/backing, clearing and missed generations invalidate the screen image. Seamless/reference views, view-only motion, disabled cache and over-budget dimensions use the existing direct presentation path. Unchanged WebGL2 content can retain its preserved drawing buffer. Explicit WebGPU canvas refreshes copy the retained viewport image into a current texture. Automatic formal batches with no changed screen pixels do not acquire a current texture or issue a screen copy; the previous completed display remains visible. The pixel harness captures submitted canvas writes in the same task, before automatic expiry: waiting for the completion callback first intermittently read an empty canvas even with the original direct renderer. Extra checks request unchanged cached frames after a task boundary.
4. Final ended feedback stays visible while its private canonical coverage is computed. Do not recompose the same tile just because intermediate private coverage advances. Every strict tile commit, missing/unfinished feedback, surface mismatch and affected history/cancel operation still invalidates the picture. No formal command or accepted input is omitted; completion waiters still require formal work and presentation.
5. Merge adjacent/overlapping mip/scissor rectangles without changing their pixel union. This removes redundant draws and repeated rounded-edge work. Canonical geometry, brush reconstruction, deposition equations and forced taper are unchanged.

## Sustained-load correction and honest capacity reporting

A subsequent software-GPU run completed1100 short strokes on both backends, but the100-long-stroke WebGPU run stopped after34 accepted strokes when sparse preview allocation reached268,369,920bytes. Canonical records were retained; the renderer's allocation exception was a real failure, not an accepted resource policy. The next fixed10Hz run accepted445/1100 on the candidate and408/1100 on the immutable baseline in the same VM, both with the explicit existing admission-limit status. Thus1100 offered at10Hz is not universally sustainable on these software-GPU runners. Neither retrying silently nor changing this test's label would demonstrate uninterrupted drawing.

Preflight the complete pending sparse preview footprint before allocating or advancing a stable cursor. The production256MiB preview cap stays unchanged. If it cannot fit, retain the last completed scene, preserve all dirty invalidation and canonical input/jobs, and prioritize bounded formal catch-up (up to128 batches and the existing2million-pixel work budget). Retired ended previews free capacity; then the picture catches up. The app explicitly reports that display processing is congested. Formal completion cannot acknowledge an undisplayed stroke; display completion and first-input samples remain pending until a real picture update. No shader, brush geometry, quality or saved data changes.

The dedicated artificial1MiB test retains366 actual samples across six G-pen/pencil/forced-taper strokes, deliberately holds formal work, and verifies that completing the first formal record alone cannot resolve its display waiter. On recovery, strict tiles and the complete scene must match an exact rebuild, and Undo/Redo must match. A separate full-editor12-stroke test retains732 samples and verifies contiguous Recovery under the same artificial cap.

Sustained1100-short and100-long completion runs now explicitly wait **before offering** another stroke only at the application's existing hard admission limits. Every such wait, total elapsed time, queue and memory peak is reported. These are closed-loop completion/retention tests, **not uninterrupted fixed10Hz acceptance tests**. A separate fixed offered200-stroke test reports all refusals and requires an explicit capacity status plus exact conservation of every accepted sample/record and complete Recovery. Default strict behavior of the shared stress script remains unchanged for earlier workflows. Physical Android sustained capacity remains unverified.

## Public primary sources
