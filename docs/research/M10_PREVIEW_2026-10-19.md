# M10 — 高倍率の仮線・処理分割・描画方式の選択

基準は PR #39 の `4708ffe5136ad1fa47be5909c129bb5f8fcb7869`。PR #38 `e510ea18b447a5e6d74721bd23b07acab15c391d` から20コミット先であることをGitHubとローカルの履歴で確認した。Draft・base・M01〜M09の受入状態は変更しない。M10全体の合格を意味しない。

## 原因として確認できたこと

- 従来は画面密度と倍率を掛けた仮画素でブラシを再評価していた。紙の模様を持つブラシは最大の密度を維持するため、高倍率の小さな作品範囲にも大量の計算が発生した。
- `rasterWork()` の中断点を通常更新の `raster()` が同期的に最後まで消費していた。更新通知もmicrotaskだったため、入力・画面更新へ実行権を戻す保証がなかった。
- 4000px / 6400% / 鉛筆32pxの同じ短い入力で、CPUだけの基準計測は4,520,880画素、中央値約362msの同期処理を再現した。ブラウザでは仮線用メモリ上限に到達する基準ケースも記録した。
- これは仮線の計算・停止を再現した証拠である。ユーザーの物理端末で、CPU、GPU、転送が遅延をそれぞれ何割占めるかは未測定。

## 採用した境界と変更

`IMPLEMENTATION_BASELINE`、`CANONICAL_INDEX`両形式、`IMPLEMENTATION_CHECKLIST`、Brush Foundation固定基準、Architecture V2 / Brush–Raster契約、Performance正本、M08表示境界、M10調査資料を確認した。

1. **400%以上の自動仮線は作品の画素に整列した格子で評価する。** 単に画面解像度を`1/zoom`へ丸めない。正式描画と同じ`capsuleCoverage`、`sweptCoverage`、`referenceCoverage`で、画素内の位置・筆圧・透明度・輪郭の割合を計算する。必要な表示範囲と補間の周囲だけを処理し、画面への拡大・回転・反転は既存の画像変換へ渡す。滑らかな表示／画素をそのまま見せる表示の指定も仮画像へ引き継ぐ。100%以下の従来の細線プロファイルは維持する。
2. **通常の仮線も途中で処理を返す。** 計算・表示用画素への変換を約3msの仕事へ分割する。4行単位の中断点を持ち、`scheduler.postTask`またはtimerのtask境界で入力へ実行権を戻す。確定前Undoや次の入力は、仮線の計算完了を待たない。ブラシ変更で前の一筆の格子を作り直さず、切替時の保護画像は作品座標ではなく実際の画面範囲で扱う。
3. **同じ確定部分は一度だけ消費する。** 一筆につき最新通知と再開可能な仕事を各1つ保持する。古い可変部分は中断し、確定済みの筆跡情報は保持する。途中の不完全な組合せは表示せず、以前の表示を残す。取消・画面世代・正式表示の更新で失効した仕事は復活しない。
4. **鉛筆の模様を作品座標で評価する。** 正式な模様計算やseed、重ね塗り、不透明度、入り抜きは変更しない。画面上の同じ作品画素を拡大率の数だけ再計算する処理を除く。

正式なFoundation、model、入力補正、テクスチャ関数、描画シェーダー、minification、TileHistory、保存形式は変更していない。128px履歴を維持し、文書全体の画像履歴へ戻さない。透明度が0へ量子化された仮画像の不要なRGBだけを0に揃えた。正式画像のhidden RGB規則には触れない。

削除した構造は、通常仮線の同期完走用`raster()`、その更新用microtask、および古い通知を毎回処理する仕事列。新しい通知用に古い可変部分を最後まで計算する必要はなくなった。GPU直接表示ではCPU用Canvasと画素バッファも作らず、必要になった時だけ用意する。既存の安全な正式反映・短い移行用画像は維持する。

## 自動選択

`preview-policy.mjs`が一筆の開始時にCPU仮線／GPU直接表示を選ぶ。端末名やdeviceMemoryによる速度判定はしない。

- 条件: 作品の幅・高さ、倍率と画面密度の区分、ブラシID・先端・太さ・硬さ・模様、レイヤー数。現在のGPU完了待ちと仮画像用の実メモリ圧も考慮する。
- 実行中の方式は筆跡IDに固定する。前のCPU仮線が残る間は、後の線がGPU画面の下へ潜り込まないよう今回もCPUを選び、前の線の確定を待たせない。遅れて届いた古い通知も表示順序を逆転させない。比較記録は最大48条件・各方式24件。条件の記録は2分で失効し、選ばれなかった方式も古い記録を永久に使わない。
- 安全性が確認されたCPU仮線から開始する。直近のGPU待ちがCPUの記録より遅い場合、不要なGPU試行を避ける。記録が不足または古くなった場合は、8筆以上の間隔と現在の負荷を確認し、別の一筆だけをもう一方の方式で測る。毎入力を両方式で二重描画しない。
- 比較は遅い側のp95とCPU処理時間。20%と2msの余裕を設け、小さな差で往復しない。実際に表示できたCPU記録と、未表示で待った時間の下限は分ける。
- CPU仮線が一度も表示できず50msを過ぎた場合、まだ表示していない私有の仮計算を捨て、同じ最新入力をGPUへ渡す。古い線の消失や二重表示を起こす途中切替は行わない。経路が利用不能になった場合も、筆跡の意味を捨てず代替を選ぶ。
- 消しゴム、下層、特殊な合成など、CPUで正しく重ねられない条件は既存の正式GPU経路を使用する。

`overlay=gpu`、`overlay=cpu`、`overlay=auto`で比較できる。既存の`overlayRatio`の明示値は面積比として維持する。明示した面積比では従来の画面格子を使うため、高倍率の自動格子との比較にも利用できる。

## 測定と合否の範囲

`m10-preview-review.mjs`は同じブラウザ、GPU設定、390×644 CSS / DPR3、同じ相対時刻・座標・筆圧でA=基準、B=CPU、C=GPU、D=自動を比較する。画像検査は`stroke-overlay-quality.mjs`、正式画素・履歴・再生は`stroke-overlay-formal.mjs`を使用する。

CIは4サイズ×5倍率×7ブラシ×4方式×2バックエンドの1,120ケースを各5入力・1筆で実行する。これは広い条件の検査であり、各行だけで安定したp95を推定できるとは主張しない。別に4000px / 100%・6400% / 7ブラシ / 3方式 / 2バックエンドで84ケースを12筆ずつ継続する。実際にCPUへ仕事を追加する条件とGPU完了待ちを追加する条件で、自動選択が両方向へ追従することも検査する。後者は制御された負荷試験であり端末性能測定とは区別する。

CPUの表示用画素転送時刻、GPU命令の完了通知、ブラウザのスクリーンショットはそれぞれ異なる観測値。画面の発光時刻、指から光までの時間、物理GPU実行時間、VRAM、消費電力・発熱は未測定。最初の表示の時刻が採れない場合、正式完了による上限と明示する。GC、画像確保やドライバー処理が必ず3ms以内になるという保証はしない。

基準のメモリ失敗は失敗として残し、比較可能な数値を作って補完しない。途中版の探索測定を最終HEADの合格根拠にしない。最終結果はQAの`evidence/preview/qa-status.json`、詳細は同じ場所の各JSONと画像を参照する。正式な画素は同一バックエンドの基準と完全一致を要求する。作品格子のCPU画像と厳密参照の誤差はRGBA8の1段階以内。仮線の比較は基準より悪化しないことを確認し、許容差を大きくして合格させない。

## 公式資料

Krita公式の[Instant Preview](https://docs.krita.org/en/reference_manual/instant_preview.html)は、通常画像と高速な仮表示を分け、効果がない倍率や小さいブラシ、模様などで制約があることを説明している。仮表示を常時強制しない判断を採用した。他アプリの非公開アルゴリズムを推測して採用していない。既存の[性能正本](../architecture/FEATURE_PERFORMANCE_RESOLUTION_2026-10-04.md)と[M10公式比較](M10_BRUSH_QUALITY_RESEARCH.md)の採用境界を維持する。
