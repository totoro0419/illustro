# M10 ゼロティック操作 — 原因調査記録（2026-10-22）
基準: PR #42 `73f9465b022cb29b1e3f9462b3d51aca3756ba6d`。失敗作PR #43は参照のみ。本番/既存PR不変更。

## 観測済み
- ユーザー実機で「太い鉛筆/Gペンの後、線が正式に確定するまで画面を動かせない」と報告された（特に4000x4000px・スマートフォン）。
- PR #41の旧CanvasNavigationでは、2本目のタッチを処理する前に`BrushSurface.finishStroke()`が呼ばれ得る。
- PR #41には`DrawingHost.picture() -> await shown`、特殊表示の`waitPrecise`がある。ただしこれだけで入力が待たされることは証明されていない。
- `DocumentPresentation.apply()`は512px画像群をメインスレッドで同期転送する。`presentation.worker.mjs`もGPUを使って画面全体を再生成する。
- PR #43の`IndependentScene.visibility()`は位置変更で完成画面画像を隠し、見かけ上「動かない・描画が消える」結果を生じ得る。
- 以前のPR #43の「描画停止」検査は、実際にはGPU送信後の仕事の完了通知を待たせている。GPUの長時間占有を再現していない。

## 未確定
上記のどれが実機での操作不能の**直接原因**か、実機CPU/GPUトレースがないため未確認。単一原因とは限らない。以前の自動テスト成功は実機解決の証拠にならない。

## 調査の分離
1. PR #41実装を改変せず、4000px・太いブラシ・複数ストローク・CPU制限でネイティブタッチの録画と入力・表示タイミングを測る。
2. イベントが入力処理まで到達したか、CanvasViewが変更されたか、実ピクセルが連続して変化したかを**独立に**判定する。
3. 同じ試験でGPU/メイン占有を計測する。ブラウザーのエミュレーションは実機と別結果として記載する。
4. 原因が特定されないときは「未確定」を維持し、次の実装では全候補の経路を構造的に切断する。新システムの独立性は新規テストで再測定する。

## 要求から導ける設計制約
- 操作イベントで現在の表示位置を同期変更する。Workerからの描画結果・GPU fence・保存・Undo等を一切参照しない。
- 終了やキャンセルを含む正式描画の仕事は、操作位置の変更より後に処理し、操作をブロックしない。
- 表示済み画像を操作のために隠さない。512px文書空間画像は新しく露出する領域の基準として保持する。
- 1イベント内で大量の画像群を転送しない。整合した表示の切替と入力経路を分離する。
- Worker停止試験（完了通知停止ではない）と、実際のGPU負荷試験を独立に用意する。
