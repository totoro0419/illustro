## PRの受入チェック

**提出時に担当側が記載する項目**

- 既存の問題ID、修正前の現象、期待する結果、採用する方式と理由。
- 変更全ファイル、データ形式・公開API・他担当との依存関係。
- 実行した確認方法と結果。未実行のテスト、未確認の実機挙動、既知の制限はそのまま記載。
- main.tsに必要な接続変更の提案と、既存のUI操作・保存との関係。

**統合担当が1PRずつ実施する項目**

1. PRのbase/headと開始点を確認し、変更対象が担当範囲内か、余計な巻き戻しがないかを見る。
2. 共通ファイル、同じ機能の二重実装、依存変更、`main.ts` の変更有無を確認。必要ならPRに差し戻しコメント。
3. ドキュメントの129 ID、作品データ、保存/復元、Undo/Redo、ペン/指と表示の挙動を壊さない設計か確認。
4. 変更に応じたテストを実行。標準のCIは `npm ci --ignore-scripts --no-audit --no-fund` → `npm run prep:check` → `npm run brush:build` → `npm run core:check` → `npm run brush:regression` → `npm run editor:build` を実施する。編集画面の単体テストと実ブラウザーの確認は変更内容に応じて追加。
5. **失敗を直すまでマージしない**。CI結果を確認し、関連IDの修正内容と未確認事項を `STATUS.md` に記録する。
6. 競合や依存関係を解消し、全体への影響を検査してから統合ブランチだけにマージ。次のPRを改めて現行の統合HEADに照合する。

CI成功・ソースレビュー済み・実機合格は別々の状態として記録する。GitHub Actionsは実機検査の代わりにはならない。

## 検査対象の考え方

- すべての取り込み：編集画面ビルド、Coreとブラシの回帰、コンフリクト有無、PRの対象IDの照合。
- レイヤー/履歴/保存系：既存作品の開閉、復元、破損時の扱い、Undo/Redoを重点確認。
- 選択/変形/塗り/定規/ベクター/文字：結果の画素、未確定表示、正式確定、キャンバス上の操作とデータ保存の一致を重点確認。
- 性能系：実機で測れない数値を「改善済み」としない。機械的なビルド成功を応答性向上の証拠にしない。
- 公開物：`main`、本番公開URL、既存合格済み成果は、別途明示された承認がない限り更新しない。
