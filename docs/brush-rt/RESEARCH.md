## Browser primary sources

- [Pointer Events 3](https://www.w3.org/TR/pointerevents3/): raw updates, coalesced samples and predicted events. Predicted samples are provisional; algorithms and horizon depend on UA. Never ingest pointermove and pointerrawupdate as independent physical streams. Feature availability and actual returned predictions are separate observations.
- [WebGPU specification](https://gpuweb.github.io/gpuweb/), [GPUWeb queue discussion](https://github.com/gpuweb/gpuweb/issues/3762): a submitted command buffer cannot be canceled with a standard API. Completion is not compositor presentation. GPU throttling must happen before submission.
- [Chrome WebGPU support](https://developer.chrome.com/docs/web-platform/webgpu/overview): support depends on OS/GPU; Android conditions apply. Runtime adapter/device probing is necessary; WebGL2 remains the compatibility backend.
- [WebGL2 specification](https://registry.khronos.org/webgl/specs/latest/2.0/): instancing, texture targets and sync polling support bounded submissions. A fence proves GPU work, not photons.
- [Chrome desynchronized canvas](https://developer.chrome.com/blog/desynchronized), [WHATWG canvas](https://html.spec.whatwg.org/dev/canvas.html): a low-latency hint may bypass compositor work. It is a hint, can be unavailable and can have tearing/flicker conditions. WebGPU has no equivalent `desynchronized` context attribute.

## Engineering judgments derived from the sources

1. Adopt temporary display separate from accurate deposition, supported by CSP's public temporary preview and Krita's explicit foreground/background feedback.
2. Use latest-state mailbox **before** GPU submission. Neither WebGPU nor WebGL can erase already submitted work.
3. Keep accurate, ordered brush commands; spend a bounded tile/command quantum behind each live frame. A second canvas/context alone is not a physical GPU priority guarantee.
4. Use continuous capsules for eligible hard round/constant color brushes; instanced shapes for transient complex feedback; accurate shader stamp deposition for complex confirmed output. This is an Illustro decision, not a claim about ibis/CSP internals.
5. A bounded local regression smoother, corner reset, optional speed component and short guarded prediction are evaluated against raw geometry; no One-Euro dependency. Strong smoothing cannot preserve every raw detail while suppressing jitter; deviations must be bounded and visible.
6. GPU completion/readback and a following animation frame are software proxies. Actual visible-tip / pen-to-photon needs real GPU, stylus and high-speed camera; software results never close that gate.
