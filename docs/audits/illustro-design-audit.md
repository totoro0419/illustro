## 2. 総合評価と優れた点

目標は正しく優先され、全247機能を常設ボタンへ押し込まず、旧UIのRail/中央Canvas/右Workspace/固定操作/Quickの構造を保持している。原仕様の30分野と現在の対象・限定・保留・対象外の境界も一致した。高度水彩を通常描画の成立条件にしない判断は、主要制作の軽さという優先順位に沿う。

アーキテクチャの良い点は、抽象語が多いことではなく、次の反例を明示的に禁止していることである。

- 計算完了順をUndo順にしない。A未完→B→UndoはBを対象にする。
- Save(A)→Undo(A)で保存対象をUndo後の像へ書換えない。用途参照と到達根を分ける。
- GPU表示キャッシュを唯一の作品正本にしない。Device loss時の再構成元を保護する。
- 正式結果追加と対応仮線除去を一つの表示世代にまとめる。二重/空白/crossfadeの半透明変化を避ける。
- 入力必要範囲と出力dirtyを分け、位相/変位/全体統計は全域へ波及し得ると認める。
- 上下二枚RGBAの合成が常に成立するとはせず、Multiply/通過Group/Clip/色丸めで依存評価へ戻す。
- 未使用機能の宣言と処理本体の起動を分け、検索しただけでAI/codec/領域解析を起動しない。

新規モデル試験でも、保存操作集合の固定（M03）とSession取消で独立Cを残すこと（M04）は成立した。これらは抽象モデルの肯定結果であり、正式画素やストレージへ一般化しない。

最も弱い箇所は、**文書で分けた意味と、操作可能な試作/型の境界が一致していないこと**である。特にUndo・層・Focus・Session確定を壊した状態では、直感性の最終確認へ渡せない。

## 4. アーキテクチャ全体の整合性

### 責務・所有・依存

|境界|確認できた整合|残る問題/成立条件|
|---|---|---|
|UI/Command|同じfeature内でもadd/select、copy/cut/pasteをactionで分離する方針|全action宣言と経路の実体がない。generic kindではAUD-001が起きる|
|Input/View|接地時対象/設定固定、予測は表示専用、ナビは正式列へ入れない|DEC-02の継続/休止は未閉鎖。時刻付き姿勢と入力の配送順を実測する|
|Admission|世代/read-write/版/予約を検査し、曖昧な対象を推測しない|文書外scope型（AUD-005）と接地中予算（AUD-014）を明確化|
|History/Revision|論理受理とmaterialized root、Sessionと作品を分離|資料/試筆等の履歴焦点（AUD-016）、受理済失敗の出口（AUD-015）|
|Evaluator/Scheduler|品質・入力域・依存・用途・予約を宣言。FIFOを保持|各処理の最長非分割区間/予約見積の実行可能性は未検証|
|Document/Cache|原本/正本/派生/一時候補を分離、保持根を保護|後段消去/下地依存筆の意味（AUD-006）。全正本種別のschema/移行は未確定|
|Presentation|同世代handoffと被覆、対象層位置への仮寄与|全blend/erase/Clip/Groupで成立するプレビュー経路は未採用|
|Persistence|Fence/pin/差分/検証/旧世代、S1/S2の逆転防止|APIの原子性・耐久性・quota/多重起動・失敗後の収束は未証明|
|Assets/IO/Recorder|旧資源版/公開除外/内部Clipboard、外観と編集性を区別|依存閉包のGC、外部codec/不足フォント等の統合試験が必要|

論理所有者をWorker個数へ固定していない点は妥当。ただし「同じ境界契約なら共通化できる」ことと、「汎用グラフを通しても軽い」ことは別である。Inputの各サンプルは専用writer、UIの可否は小さいメタデータという方針を維持する。

### 統合時に確認すべき反例

1. **Save pinと資源競合**：大きなAをSaveが保持、Undo後Cを受理、Aの完成先に追加メモリが必要。予算を持つJob同士が待つと、ナビは動いても正式化/保護が停止し得る。循環待ち禁止の原則はあるが、token割当/解放/予約不能時の救出をT03/T06で検証する。これは発生済みデッドロックの報告ではない。
2. **Layer属性と受理順**：半透明A処理中→不透明度変更→B。Aの入力固定、Layer属性の作品内作用位置、Bの参照下地が一致しなければ、同じ操作列でも見た目が変わる。read/write宣言を個別演算へ落とす必要がある。
3. **Sessionと独立編集**：変形候補A→別層C→内部Undo/作品Undo/取消。候補値だけの変更、Cの取消、候補A全破棄を別々に検証する。現試作の全Undo占有はAUD-003。
4. **失敗と保存**：A→依存B→独立C→Save→A恒久失敗。Cを保護したままBの扱いと旧Fence失敗/新Fence救出を決定する（AUD-015）。
5. **外観依存とGC**：素材削除→旧Redo→Timelapse→別端末Native。使用版の到達根と、現在庫の削除を別に扱う。保存確認が終わるまで旧正常世代の依存を回収しない。
6. **変形後の筆**：source→transform→postPaint→laterTransformという順序だけでは、erase/smudgeの作用と旧transform変更時の意味は完結しない（AUD-006）。格納方式より先に期待像を決める。

### 正確性と障害復旧

Undoでcurrent用途だけが不要になっても、Save/Snapshot/Recovery/Recorder/Clipboardが必要とする結果は残す方針は整合している。古いJobを一律破棄するLabコードを製品へコピーしてはいけない。公開検査ではDocument/Target lifetimeだけでなく、依存/設定/品質/色/Device世代を照合する。

一方、型案の`failed`は宣言された終端に近く、依存履歴・保存・再試行不能時のUXに具体的な出口が不足する。失敗を無条件に巻戻す案、Saveを現在rootへ差替える案、空白を正式像として成功にする案は採用しない。

保存schema/APIを未固定としていること自体は欠陥ではない。実装前に、変更ブロック→manifest→世代公開→確認、の各段階でプロセス停止を注入し、前世代/新世代のどちらを有効とするかを具体化する必要がある。`verified`の名称だけで電源断耐久性を保証しない。

容量の算術例として8192² RGBA16の密な一面は512MiB、5面なら2560MiB。これは計算例で、常時その量を確保する設計だという指摘でも、実測値でもない。入力保持・仮表示・正式出力・Undo・Save pin・codec一時領域のピークを同時に見積もる必要がある。固定「5層」や旧128/256pxを採用してこの問題を解決済みにしない。

現在の資料は遅延値/端末上限/近似許容差を未確定と正直に記す。これ自体を「実装なしの欠陥」とはしない。ただし**計測前に条件と合否線を登録しなければ、T01–T08を実行しても製品性能の採用判断は閉じられない**。同品質の競合/参照系、p50/p95/p99/最悪停止、最古筆の前進、熱/電池、長時間を含める。

G0/G1を満たす前に「全機能の実装へ一括着手」しない。G2以降は実装候補を比較するための限定試作であり、全エンジンを先に完成させる条件ではない。数値は根拠なく埋めず、代表端末/作品/比較相手/誤差/反復を決めてから採用判定を行う。
