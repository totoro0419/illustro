## 1. 運用と完成判定

1. 各IDの所有Cを一意に決める。横断する他機能は依存関係として扱い、同じ能力を重複開発・重複計上しない。
2. `features.json` の**個別仕様**から、処理/画面入口/パラメータ/候補表示と確定取消/Undo・再編集・保存/失敗時/状態更新を**個別に検証**する。付属JSONは、236件それぞれの7つの確認観点を実装作業として保持する。該当する詳細が不要な場合だけ、その理由を記す。
3. 既存のコードが要件を満たし、適切なテストで立証された部分は**再実装しない**。不足・不具合があれば、その部分だけ修正・テスト追加。
4. 成果の判定は「完成を裏付ける検証あり」「一部実装・不具合」「未実装」の3区分にし、別に「未検証・検証不能」と理由を記録する。コードやテストの存在だけで完成にしない。
5. 既存827操作検査の合格結果を**対象操作の証拠としてのみ**再利用し、他のIDに転用しない。歴史的な91件A判定などを無条件のPASSとしない。
6. C01〜C10の不足はC01〜C10の所有者がまず閉じる。C11〜C16は残りの製品機能。C17は全機能を横断する実機・性能・保存復元・品質ゲートで、未実装機能の押込み先にしない。
7. PR #107の旧155件調査は**再評価が必要な履歴**として保持。旧設計の判定/年月日で新正本の仕様を上書きしない。製品コード・正本はこの計画PRでは変更しない。

### 特に注意する代表機能

- **FIL-001 通常塗りつぶし（C08）**：ボタンと処理の存在だけでは完成ではない。タップ/ドラッグで範囲を指定→正しい画素に反映→取消・Undo→保存復元まで通す。通常バケツの追加確定操作が直感性を損なっていないかも評価。
- **FX-125 Median・ごみ取り（C13）**：Medianとごみ検出を分離し、半径・ごみサイズ・閾値・局所マスク・誤消去からの復帰・効果再編集を検証。
- **FX-007 修復・パッチ・クローン（C13）**：Healing / Patch / Cloneを個別操作として検証。採取元/適用先・複数層参照・整列モード・一操作一Undo・元画像保護を検証。
- **CAN-005 / CAN-010（C06）**：キャンバス外の画素を本当に保持・再表示できるか。Crop後の見た目だけで認定しない。
- **COL-011（C04）**：知覚的色選択・色域マスクは旧調査で未実装と判断されていた。現行コードで再確認し、足りなければ実装する。
- **WET-002 / WET-005（C11）**：最終採否は**限定採用**。時間進行する水/顔料物理は含めない。見た目の水彩風表現と紙テクスチャを対象にする。

## 5. 実装担当への引継ぎ形式

各担当はJSONのIDと作業単位を読み、**現在の実コードを先に照合**する。
- 完了できたもの：処理箇所・UI入口・検査入力と期待/実測結果・Undo/再読込の証拠とHEADを残す。
- 不足があったもの：具体的な不成立条件、修正箇所、依存ID、検査の追加と再実行結果を残す。
- 確認できないもの：理由・検査が足りない条件・次の担当を別欄に記す。機能不存在の断定にも「完成」にも流用しない。

**この文書・JSONは「正式対象の割当が揃ったこと」のみ機械的にチェックした計画。236機能の実装・操作・実機の完成を確認したものではない。**
