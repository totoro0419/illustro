# Brush Foundationの完成条件

今回の最終目標は、実機で合格した軽さ・追従を保ち、今後のほぼすべてのブラシが共通利用できる基盤を成立させること。CI、HTML更新、7本の起動だけでは全体完成としない。

優先順位は直感的操作、使いやすさ・軽さ、多機能。大手の公開された優れた方法を積極的に取り入れ、非公開の内部実装を断定しない。

## 完成を判断するための対応表

| 条件 | 共通の実装と確認方法 |
|---|---|
| Gペン・丸ペン・ミリペン・マーカー・鉛筆・硬い/柔らかい消しゴム | `referenceBrushes` の設定。ブラシIDで描画を分岐しない。共通の入力・設定・命令・描画・再生を使用。 |
| 筆圧・入り・抜き | 端末/ブラシ曲線、独立した筆圧平滑化、共通Dynamics、描画中に決まる開始/終了曲線。離した後の延長/細線化はしない。 |
| 手ブレ補正・Prediction | 共通/ブラシ別の補正、速度による調整、上限付き表示専用予測。予測は保存しない。 |
| Brush Dynamics・Tip・Spacing・Rotation・Aspect | 共通設定と `evaluateDynamics`。画像マスク・時間/距離間隔・角度の短い方向の補間・粒の配置。 |
| Opacity・Flow・Blend・Erase | 一筆の濃さと押印ごとの量を分離。normal/erase/multiply/screen。連続MAX面と順序付き重ね塗りを設定で選択。 |
| Texture・Grain・Random・Scatter | 紙/先端座標の画像・手続き模様、再現可能な乱数、粒の数・散布・偏り。builtinで同時に評価する質感層は1層。 |
| Preset・Save/Load・Undo/Redo・Deterministic Replay | 版付き設定/記録、資源埋め込み、入力/seedによる命令再生成、GPUの復元画面との比較。変更/読み込みに失敗しても直前の設定を保つ。 |
| 最初から完成した線が付いてくる | 描画中、離した直後、正式描画、復元画像の比較を機械検査。実画面で切替が見えないことと自然な描き味はユーザー確認が必要。 |

実装の存在、機械検査の合格、実機での受入を別々に記録する。最新の結果は `VALIDATION.md`、51項目の詳細は `REQUIREMENT_COVERAGE.md`。

| 追加するもの | 再利用する仕組み | 追加時に必要な仕事 |

| Image/Decoration/Scatter/Custom Pattern | 画像先端、画像/手続き模様、向き、散布、再現可能な乱数 | 資源/プリセット/編集UI/用途に応じた品質検査。色付き画像は追加の描画提供者が必要。 |

`foundation-contract.test.mjs` は画像先端＋模様＋散布、時間間隔＋重ね塗り、別の描画提供者を設定の組合せで実行する。別提供者をmainと実際のcanonical workerの両方に登録し、同じ記録が生成されることまで確認する。これは将来の全効果・全端末で性能が成立する証明ではない。

## 提供者を追加するときの契約

1. 同じIDの `RendererRegistry.register` をmainとcanonical workerの両方で実行する。
2. アプリは登録処理を含むworkerモジュールURLを `RealtimeSession` に渡す。標準workerには追加提供者が自動登録されない。
3. 読み込み/再生前にもmainで提供者を登録する。ない場合は明示的なエラーとし、通常インクへ置き換えない。
4. builtin互換の提供者は共通のcompiled materialを返す。特殊シミュレーションはbackend/正式処理の実装も必要。
5. ソース設定・拡張設定は記録に残す。提供者の意味が変わる変更には新しいID/版と互換検査が必要。

登録・workerの実行例は `packages/brush-rt/test/fixtures/test-material-provider.mjs` と `provider-worker.mjs`。試験用の供給量変換であり、水彩の代替実装ではない。

## 全体の受入

自動検査が合格した版を、以前合格した版と同じ端末・ペンで比べる。`HUMAN_CHECKS.md` とページ内の平易な確認項目を使い、筆圧、入り抜き、細い形、太い線の追従、予測の外れ、離した後の変化を確認する。確認結果がない項目をPASSとしない。

受入後は個々の特殊ブラシと上位機能を追加する段階へ移る。今回の変更で描画全体を作り直すことを次の前提にしない。
