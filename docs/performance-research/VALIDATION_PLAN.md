## 共通の記録形式と正しさoracle

各runは候補ID、commit、OS/browser/runtime build、CPU/GPU、driver、RAM、画面物理/論理px、refresh周期T、入力装置/センサー可否、電源/電池/温度、作品のhash/寸法/層数/深度/ICC/効果深度/資源数、cold/warm、seed、試行順、時刻と測定誤差を残す。

入力源（実機配送と既知のreplay列を区別）→handler開始→意図受理→初めて対応する画面反応→追従中の位置/年齢→意味的確定→保護完了→export検証を別々に記録。JS callbackだけの値をpen-to-photonと呼ばない。画面反応は高速度撮影/外部マーカー等の利用可能な測定で照合し、カメラのframe量子化誤差を付ける。callbackが無い区間を入力が無かったと推定しない。

- input received/admitted/committedのIDと件数を照合。重複と欠落を別に数える。途中予測点を実測点数へ含めない。
- p50/p95/p99は生データとサンプル数、nearest-rankなどの定義、最悪停止と発生条件を併記。少数サンプルのp99を安定推定値としない。
- 追従は入力年齢、先端までの距離、変換座標の誤差、確定待ち列長と最古待機年齢。平均FPSだけにしない。
- 処理完了時間は受付から確定、保存/復元は別。並列で早く見えても総仕事や保護の遅れを隠さない。
- CPU（core/総時間）、GPU（計時可能範囲/提出待ち/転送）、memory（CPU/GPU/一時peak/保護pin）、電池/温度（同画面/輝度/時間/初期温度）を分ける。測れないメトリクスを0と記録しない。
- 整数画素と構造/Identity/参照/操作順/Undo/保存境界は厳密比較。floatの数値誤差と知覚差は別。誤差許容は基準画像・深度・空間別に事前設定し、試験後に合格へ合わせない。
- 正解は単純逐次処理、全域評価、原状態再読込など別経路で作る。同じ最適化をoracleへコピーしない。意図が曖昧な領域認識は作者/正解付き絵で採否を確認しスコアを正解としない。

## 性能目標の扱い

**以下は試作比較用の暫定目標案で、達成値でも正式な製品合格線でもない。** 数値根拠は未取得で、refresh周期を基準に測りやすくした仮置き。まず低負荷の単純表示器と競合の同条件分布を測り、達成可能性と作者の許容度から見直す。

| 指標 | 暫定目標案 | 正式確定前に必要な根拠 |
|---|---|---|
| ナビ受付→対応する初反応 | p95≤2T、p99≤3Tを最初の試作探索目標 | 入力配送遅延/外部映像/refresh、低性能端末での実測。0ms保証ではない |
| 継続ナビの追従 | 作品・途中線・枠の同一変換、p99を単独ナビから不必要に増やさない | overlap時と単独の差、位置誤差、利用者比較。差の許容量は未確定 |
| 受理済入力/誤対象/保存破壊 | 欠落0・誤対象0・正常原本破壊0 | 有限試験内でゼロを確認。全将来の無故障保証ではない |
| 確定結果 | 整数/構造は基準一致。float/近似は事前定義した誤差内 | 演算/色域別oracle。未確定の近似許容を理由に自動採用しない |
| 処理完了/保護待ち | 応答改善の代わりに無限に増えない。持続入力後も待ちが回収可能 | 操作需要と処理供給の測定、最古待機/未保護量の上限。数値は未確定 |
| 未使用機能の費用 | 主筆とナビの分布、起動、memory、電池/熱で悪化原因を説明し不要仕事を除去 | OFF/未使用文書/使用中文書の比較と測定ノイズ。未測定でゼロ負荷とは言わない |
| 手数/直感性 | タスク成功率を落とさず対象探索/やり直しを削減 | 初見と習熟、PC/Tablet/Phoneの課題評価。人数/許容差をpilotで定義 |

採用は正しさと安全を必須gateにし、同じ品質の基準より応答/総時間/資源/操作負担のどれが改善し、何が悪化したかを示す。数値だけでなく失敗場面の動画/差分を残す。優越が決まらない場合は維持費の低い案を比較候補とするが、ユーザー発案との比較を閉じない。

## 実施順と客観比較

1. 単純な参照実行と計測器の誤差を検証。モデルE01〜07はここまでの一部。
2. T01/02/06/07/10の最小独立試作で入力/状態/予算/保存/色の破壊条件を先に探す。製品本体へ実装しない。
3. 同じfixture・同じ端末・同じ品質でA/B/Cと参照をcold/warm反復。最初は少数pilotで分散を調べ、必要サンプル数を決める。thermal安定、試行順の無作為化、再現可能な入力列を記録する。
4. T03/04/05/11/12を重ね、2h/8h候補で蓄積・保護飢餓・メモリ回収を検査。失敗した組合せを平均値へ埋めない。
5. 利用可能な競合（指定7製品）を同じ入力/作品/タスクで比較。OS/端末の違いがある測定は別群にし、競合に対応機能があると未確認のまま仮定しない。単純な処理速度だけでなく同じ完成品質までの総作業を測る。
6. ユーザー自由案を同じ候補ID/条件/反証点で追加。技術語の完成度や提案者で扱いを変えない。採用判断を記録してから正式設計へ進む。
